# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## Right to Speak («Право голоса») — модуль для Foundry Virtual Tabletop 14

**Редакция:** 3.1 (единое самостоятельное ТЗ) — 09.10.2026  
**Статус:** согласованное техническое задание для разработки; **не готовый модуль**. Изменены требования к хранению закрытых заявок после замечаний Codex по V14.364. Техническая безопасность адресного обмена пока не подтверждена реальным сетевым испытанием.  
**Целевая платформа:** Foundry VTT, основная версия — **14**.  
**Язык интерфейса:** русский; английский — вторая локализация.  
**Игровые системы:** любая. Проверять в том числе на VTM V20 и фэнтезийной кампании.  
**Название пакета и ID:** Right to Speak / `right-to-speak`.

> **Главное назначение:** игрок без голосового перебивания сообщает мастеру, что хочет высказаться или вмешаться в текущую сцену. Мастер видит причину, срочность и связанные заявки и управляет очередью. Особый режим позволяет сообщить намерение только мастеру, не раскрывая его остальным.

## Как использовать это ТЗ

Это **единый документ** для передачи Codex. Он заменяет разрозненные пояснения о приватности. Требуется реализовать весь функционал из разделов 1–14, учитывать Приложение A и провести доступные проверки. **Не менять существующие исходники проекта только ради редактирования ТЗ**; отдельным заданием на разработку исходного кода будет сама реализация модуля.

**Правило выпуска:** наличие адресного API ещё не доказывает, что секретная заявка не попадёт посторонним клиентам. До проверки в трёх независимых клиентах V14.364 приватный режим считается **экспериментальным и не подтверждённым по безопасности**. Для локального прототипа допустимо собрать ZIP с явной пометкой BETA, но приватный режим не должен по умолчанию обещать проверенную защиту. Если реализация адресного обмена раскрывает содержимое посторонним, режим должен быть отключён без замены на широковещательный сокет.

# 1. Что входит в версию 1.0

**Обязательно (MUST):**

1. Две основные кнопки: **«Слово»** и **«Вмешаться»**.
2. Тип срочной заявки: **Действие / Поддержка / Контрдействие / Уточнение**.
3. Необязательная привязка к **другому пользователю** («помогаю», «противодействую», «уточнение относительно действия»), без привязки к механикам системы.
4. Необязательный текстовый комментарий (до 240 символов).
5. Отправка публичной либо приватной (**«Только мастеру»**) заявки. Режим приватности выбирается **до** отправки.
6. Плавающая сворачиваемая панель; индивидуальное сохранение позиции и состояния для каждого участника.
7. Отдельный интерфейс мастера с очередью, категориями, фильтрами и действиями **«Увидел», «Дать слово», «Завершить»**.
8. Обновления состояний автору и допустимым наблюдателям без спама в общий чат.
9. Восстановление публичной очереди после обновления страницы / переподключения; приватной — в пределах того же профиля браузера GM с обозначенными ограничениями (§7, §11 и Приложение A).
10. Поведение при двух ведущих, отсутствии ведущего, повторных нажатиях, ошибке доставки и конфликтах действий.
11. Темное минималистичное оформление по согласованным скриншотам Foundry (см. §8).
12. Полная проверка запрета разглашения тайных заявок (см. §11).

**Не входит:** кубики/броски, управление боем и инициативой, дисциплины VTM, изменение листов персонажей, интеграции с Discord/голосовой связью, отдельная механика «X-карты» или экстренной остановки игры по причинам безопасности. Последнюю нельзя маскировать под игровую срочность.

# 2. Термины, роли, уровни срочности

- **Пользователь** — учётная запись Foundry (`User`); не токен, не Actor, не персонаж.
- **Автор** — отправивший заявку игрок.
- **Мастер / GM** — пользователь Foundry с ролью Game Master; видит все заявки.
- **Заявка** — одно активное намерение игрока, отражаемое в очереди.
- **Обычная** — запрос слова: можно подождать своей очереди.
- **Срочная** — игровое вмешательство: мастер должен заметить его до продолжения сцены.
- **Публичная** — карточка (без приватного комментария) видна другим игрокам.
- **Приватная** — информация доступна только автору и мастерам; третьи игроки даже не знают о её существовании.
- **Статус** — стадия обработки мастером; **тип** — что именно намерен сделать игрок. Не смешивать.

**Важное правило:** «Вмешаться» означает *предложение прервать развитие сцены*, а не право автоматически остановить ведущего, взять управление другим персонажем или применить игровое правило.

# 3. Действия игрока: детальные сценарии

## 3.1. Кнопка «Слово»

**До нажатия:** видно постоянный переключатель «Только мастеру» (выключен по умолчанию, если игрок ранее не выбирал иначе). Других обязательных полей нет.

**При первом нажатии:**
1. Создается заявка `urgency=normal`, `category=word`, `status=pending`.
2. В интерфейсе автора появляется «Ожидает»; кнопку нельзя использовать для размножения заявок.
3. Мастер получает новую запись в обычной очереди.
4. Если заявка публична — другим видны автор, обычный тип, время ожидания/очередь и разрешенные статусы. Если приватна — ничего о ней не показывать и не передавать.

**Повторное нажатие:** открывает карточку текущего запроса вместо отправки второго. Отмена — отдельным действием с понятной подписью.

## 3.2. Кнопка «Вмешаться»

**При первом нажатии:** незамедлительно отправить `urgency=urgent`, `category=intervention` («Вмешательство», тип не уточнён). **Не ждать** выбора категории и комментария. Мастер получает заметный, но короткий визуальный сигнал.

**После отправки:** показать компактную область уточнения (не модальное окно):
- Действие — заявить собственное действие;
- Поддержка — помочь/поддержать другого участника;
- Контрдействие — попытаться воспрепятствовать чужому действию;
- Уточнение — спросить мастера до продолжения сцены.

Категорию разрешено не выбирать: первоначальная заявка всё равно действует. Изменения дополняют **ту же** запись и не повторяют тревогу. Автоматическая отправка по каждому символу запрещена; подтверждение «Сохранить» или debounce с гарантированной согласованностью.

**Если уже отправлено «Слово»:** нажатие «Вмешаться» повышает срочность существующей заявки после понятного подтверждения или явной индикации; время исходного создания не меняется. Нельзя обходить антиспам постоянным чередованием режимов. Если уже есть срочное вмешательство — открывать его редактор.

## 3.3. Привязка к другому игроку

Поле **«Связано с участником»** содержит активных пользователей Foundry, кроме автора; поиск по нику. Не показывать Offline по умолчанию (в уже созданной записи имя offline-участника сохраняется). Поле необязательное.

Примеры мастеру:
- «Маркус — Поддержка → Винсент»;
- «Эдрик — Контрдействие → Маркус»;
- «Винсент — Действие» (без цели).

Связь означает только игровой контекст. **Она НЕ предоставляет целевому игроку доступ** к приватной заявке, комментарию, статусу или скрытому существованию запроса. Ссылка на другую конкретную заявку может добавляться только при наличии у пользователя права её видеть. Достаточно обязательного поля `targetUserId`; автоматическое объединение цепочек — необязательное улучшение.

## 3.4. Комментарий

Необязательное текстовое поле до **240 символов**, без HTML и форматирования. Примеры: «Хочу перехватить NPC до ухода», «Поддерживаю его предложение», «Против его выстрела». Не должно занимать экран постоянно; открывается в редакторе.

**Правило конфиденциальности:** даже при публичной заявке комментарий по умолчанию доступен только автору и мастерам. Другие видят публичную метку намерения и цель, но не произвольный текст. При необходимости публичные комментарии можно предложить в будущей версии, не в MVP.

## 3.5. Приватная заявка

Переключатель **«Только мастеру»** размещён непосредственно рядом с двумя кнопками и виден *до* любого нажатия. Он не должен требовать открытия вложенного меню. Запоминается локально для конкретного игрока.

- Приватное «Слово» — личный запрос к мастеру.
- Приватное «Вмешаться» — скрытый сигнал с возможностью уточнить тип, цель и комментарий.
- Другие игроки не получают ни самой записи, ни уведомления, ни изменения публичных счётчиков, ни маркера «скрытый запрос».
- Мастер видит обычную карточку с маленьким замком и может отвечать штатными действиями.
- Автор видит свою заявку и её обработку.

**Изменение публичности:**
- `private → public`: явное подтверждение, только затем публикация допустимой проекции заявки.
- `public → private`: предупредить, что прежние сведения уже могли увидеть и это нельзя «отменить». С новой версии записи не должны снова транслироваться публично.
- Переключение приватности уже отправленной заявки должно быть отдельной безопасной операцией, без временной публикации черновика.

# 4. Статусы и действия мастера

## 4.1. Жизненный цикл

| Статус / ключ | Текст игроку | Значение |
|---|---|---|
| `pending` | Ожидает | Запрос принят системой и находится в очереди; мастер ещё не подтвердил просмотр |
| `acknowledged` | Мастер увидел | Мастер нажал «Увидел» |
| `floor` | Тебе слово | Мастер предоставил возможность высказаться |
| `closed` | Завершено | Мастер обработал и закрыл заявку |
| `cancelled` | Отменено | Автор отозвал заявку |

Отдельные **транспортные состояния, НЕ статусы заявки:** «Отправляется», «Не доставлено», «Ошибка», «Мастер не в сети». Никогда не рисовать `pending`, пока сервер/подтверждённый механизм не принял заявку. Экран должен дать повторить безопасно с тем же idempotency key.

Разрешённые переходы: `pending → acknowledged → floor → closed`; `pending → floor`; `pending/acknowledged/floor → closed` (GM); `pending/acknowledged/floor → cancelled` (автор). Возврат к предыдущему состоянию не нужен. Зафиксировать разрешения в одном чистом reducer/автомате. Закрытая или отмененная не возвращается в активную очередь.

## 4.2. «Увидел»

Мастер нажимает по заявке «Увидел»; автор видит изменение «Мастер увидел». Это **не** автоматически «Дать слово». Ведущему нужно иметь возможность подтвердить несколько заявок и продолжить сцену.

## 4.3. «Дать слово»

Мастер обозначает участника, которому сейчас можно говорить. У автора явно появляется «Тебе слово», у остальных — только допустимая публичная индикация (тайная заявка по-прежнему невидима). Кнопка не включает микрофон, не переключает камеру и не вмешивается в голосовой чат.

Можно иметь несколько статусов `floor` одновременно (например, два взаимосвязанных действия); не отзывать автоматически слово у одного при выдаче другому. Если нужен режим «один говорящий» — только отдельная необязательная настройка в дальнейшем.

## 4.4. «Завершить» и «Очистить очередь»

«Завершить» закрывает одну заявку, сохраняет краткий терминальный результат и убирает из активной очереди. «Очистить очередь» доступно только GM, показывает подтверждение с числом видимых **мастеру** активных заявок и закрывает/очищает их; по умолчанию это не действие для игроков.

Небольшая история по текущей игровой сессии (до 20 завершённых записей) допустима для GM и автора, но нельзя сохранять приватные данные в общедоступном журнале. Избыточную долговременную аналитику не делать.

# 5. Очередь заявок и уведомления

**Сортировка:** отдельная секция «Срочные», ниже — «Ожидают слова». Внутри секций — по времени **создания**, старые выше новых. Смена категории не меняет время. Повышение приоритета перемещает заявку в срочную секцию, сохраняя время среди срочных.

**Панель мастера:** каждая строка показывает иконку + усечённое никнейм (полный — tooltip) + тип + связанного игрока, если есть + статус + пометку приватности (только для GM) + кнопку раскрытия. Полный комментарий виден лишь в раскрытой строке. Действия не прятать за длинными именами.

**Краткий сигнал:** при новой срочной заявке у GM пульсация рамки **до 3 циклов по 0,5 с**, затем постоянный маркер. При `prefers-reduced-motion` — без анимации. Не делать полноэкранный красный фон или вечную мигалку.

**Игрокам:** публичная срочная заявка может ненавязчиво подсвечивать значок панели; приватная — только автору и GM. Звуки **выключены по умолчанию**; раздельное включение локально, короткий негромкий сигнал без принудительного воспроизведения. Отсутствие звука не должно влиять на доставку.

**Свёрнутая панель:** отображается значок/бейдж только для заявок, доступных данному пользователю. Для мастера — все; для автора — свои и публичные; для остальных — исключительно публичные. Частные запросы НЕ меняют бейдж у третьих игроков.

**Один активный запрос на игрока:** избыточный клик не создаёт дублей; вместо этого открывает текущую карточку. Лимит кратковременных повторов / повышение приоритета против спама, но первый срочный сигнал — без искусственной задержки.

# 6. Сценарии использования

**Сценарий A — очередь.** Маркус нажимает «Слово» → GM видит обычную заявку → нажимает «Увидел» → Маркус видит подтверждение → GM нажимает «Дать слово» → Маркус говорит → GM завершает.

**Сценарий B — срочное действие.** NPC собирается уйти. Винсент нажимает «Вмешаться» → GM сразу видит сигнал «Винсент: вмешательство» → Винсент выбирает «Действие» и пишет «Хочу остановить NPC» → карточка обновляется без повторной тревоги → GM даёт слово.

**Сценарий C — поддержка.** Маркус выбирает «Вмешаться» → «Поддержка» → цель «Винсент» → мастер видит «Маркус помогает Винсенту», может рассмотреть связанные заявки совместно.

**Сценарий D — контрдействие.** Игрок выбирает «Контрдействие» → цель «Маркус» → мастер видит, что действие направлено против другого участника. Модуль ничего не решает по правилам VTM и не бросает кубики.

**Сценарий E — тайное намерение.** Эдрик заранее включает «Только мастеру» → нажимает «Вмешаться» → выбирает «Контрдействие» и цель «Винсент», пишет комментарий → GM и Эдрик видят заявку → Винсент и прочие игроки не видят ни самого запроса, ни смены общего числа запросов, ни сетевых событий с секретными данными.

**Сценарий F — ошибка / обновление.** Автор обновляет браузер с активной заявкой → его заявка восстанавливается; мастер видит тот же ID, время и статус; повторный клик не дублирует. При отсутствии мастера — ясно показать это и не подтверждать несуществующую доставку.

**Сценарий G — длинный ник.** «Александр фон Рейхенбах-Старший» не выталкивает кнопку «Дать слово» за границы, не скрывает иконку и счётчик. Полное имя видно по наведению/фокусу.

# 7. Реакция на особые ситуации

1. **Нет активного GM:** кнопки отправки недоступны с пояснением «Мастер не в сети». Не копить тайные запросы в общедоступной локальной очереди и не притворяться, что они доставлены.
2. **Два и более мастера:** первичный обработчик — один назначенный активный GM. Другие подключённые GM получают разрешённую копию через адресные `User.query` (не broadcast). Изменения от других GM маршрутизируются через первичного координатора. Перевыборы GM и пределы восстановления, особенно при переходе между компьютерами, явно документировать; не заявлять абсолютную консистентность без теста.
3. **Потеря связи во время CREATE:** повтор с тем же idempotency key не порождает вторую заявку.
4. **Автор отменяет, GM подтверждает одновременно:** валидируется `expectedRevision`; выигрывает первая принятая сервером/координатором операция. Вторая получает конфликт и новое состояние.
5. **Перезагрузка GM/автора:** в v1 восстановление приватной очереди после перезагрузки **того же браузера** GM из его локального IndexedDB, автор восстанавливает свою заявку из собственного хранилища и может повторно синхронизировать её с мастером. Переключение GM на другой компьютер, сброс хранилища браузера и отсутствие одновременно доступных авторов не гарантируют восстановления приватной истории. Не заявлять о серверном закрытом хранилище.
6. **Игрок сменил ник:** ссылка по `User.id`, не по отображаемому имени.
7. **Цель вышла из игры:** карточка продолжает отображать последнюю разрешенную информацию о цели; ссылка не исчезает автоматически.
8. **Модуль выключен во время игры:** не удалять данные другого модуля или документы мира; отсутствие этого UI не должно ломать Foundry.
9. **Массовое закрытие:** подтверждение, проверка роли GM, корректная синхронизация.
10. **Текстовые поля:** защищать от вставки разметки, огромных строк, нестандартных символов; отображать через `textContent`/экранирование, а не небезопасный HTML.

# 8. Визуальный дизайн и интерфейс

# 9. Настройки

## Настройки пользователя (локальные)

- Координаты и развернутость панели.
- Последний выбранный режим приватности (по умолчанию «Публично» при первом запуске).
- Звуковые оповещения: выключены по умолчанию.
- Уменьшение анимации (принудительно, плюс уважать системный `prefers-reduced-motion`).

## Настройки мастера (мир)

- Показывать ли игрокам очередь **публичных** заявок (по умолчанию да; при выключении показывать только собственную заявку и данные, на которые пользователь уполномочен).
- Лимит завершённых заявок в истории текущей сессии: 20 по умолчанию.
- Ограничение частоты повторных сигналов; пример — не чаще одного нового запроса за 3 с и повторного повышения срочности за 10 с (настраиваемые значения, не задерживать первое вмешательство).
- Дополнительный звук разрешён, но локальная настройка игрока имеет приоритет.

Настройки модуля не должны раскрывать тайные заявки даже пользователям, которые могут просматривать данные `world` settings.

# 10. Данные, события, синхронизация

## 10.1. Логическая структура заявки

```ts
type RTSRequest = {
  id: string;                 // уникальный неизменяемый ID
  ownerUserId: string;        // фактический пользователь, не ник
  urgency: 'normal' | 'urgent';
  category: 'word' | 'intervention' | 'action' |
            'support' | 'counteraction' | 'clarification';
  targetUserId: string | null;
  note: string;               // 0..240 симв., доступ только автору и GM
  visibility: 'public' | 'gm';
  status: 'pending' | 'acknowledged' | 'floor' |
          'closed' | 'cancelled';
  createdAt: string;          // подтвержденная система времени
  updatedAt: string;
  order: number;              // присваивает авторитетный обработчик
  revision: number;           // растет при каждом изменении
};
```

Не сохранять чувствительные данные в незашифрованном общем канале по надежде, что CSS/клиентский код их скроет. Число, идентификатор, время и сам факт приватной заявки также чувствительны.

## 10.2. Операции

- `CREATE_REQUEST` — с уникальным ключом идемпотентности; приватность **сразу** в самом создании.
- `UPDATE_REQUEST` — правка категории, цели, комментария; проверка версии.
- `SET_VISIBILITY` — отдельная операция, подтверждение переходов.
- `ESCALATE` — повышение `normal → urgent` одной записи.
- `CANCEL_REQUEST` — только автор или GM.
- `ACKNOWLEDGE_REQUEST` / `GRANT_FLOOR` / `CLOSE_REQUEST` / `CLEAR_QUEUE` — только GM.
- `GET_AUTHORIZED_SNAPSHOT` — реконструкция допустимой пользователю очереди после reload.

Синхронизация по `id/revision`. Дубликаты и события в неправильном порядке игнорируются или инициируют новый снимок. Не принимать клиентское время за серверное и не доверять присланному полю `isGM`.

## 10.3. Многопользовательский режим

Активные GM получают приватные заявки через адресные `User.query`. Основной GM — координатор присвоения порядка и ревизий; остальные GM отправляют операции ему и обновляют свои локальные копии. Отсутствие серверного атомарного хранилища и возможные сбои при смене координатора — известные ограничения v1. Не пересылать закрытые сведения модульным широковещательным сокетом.

# 11. Конфиденциальность — критическое требование к выпуску

**Проблема Foundry:** `socket: true` модуля создаёт канал, который по официальной документации **транслирует сообщения всем остальным клиентам**. Поэтому схема `game.socket.emit('module.right-to-speak', {to: gmId, secret: ...})` НЕ является приватной, даже если интерфейс фильтрует получателей. Нельзя кодировать секрет в base64 и считать его защищённым.

**Согласованная архитектура v1:** для приватных заявок используется штатный адресный API `User.query` (пакетные `User.queryMany`, если удобно), запросы обрабатываются зарегистрированными `CONFIG.queries["right-to-speak.*"]` на клиентах конкретных получателей GM и автора. Соответствие именно сборке Foundry V14.364 необходимо проверить; в V14 это публичный API. Для приватных заявок НЕ использовать `ChatMessage.whisper`, общий `game.socket`/модульный broadcast, world settings или документы мира без доказанных серверных прав. Приватная очередь хранится **локально на стороне GM** (IndexedDB; на стороне автора — только свои заявки), а не в мировом публичном хранилище. Это позволяет пережить обновление страницы на том же устройстве, но не гарантирует восстановления на другом устройстве/после очистки браузера. Полный протокол и модель угроз: **Приложение A настоящего ТЗ**. Релизное обозначение «проверена конфиденциальность» возможно только после сетевого теста GM + 2 игрока.

### Обязательные инварианты

1. Неавторизованный клиент не получает содержимое заявки **и даже метаданные о её существовании** (в сокете, DOM, общем документе, settings, снимках, логах, суммарных счётчиках).
2. Приватная цель `targetUserId` не делает соответствующего участника получателем и не раскрывает ему заявку.
3. Публичный объект никогда не содержит приватного комментария; отображается только разрешённая публичная проекция.
4. При приватной заявке все подтверждения (`ack`, `floor`, `closed`) доставляются только автору и GM.
5. Нельзя строить авторизацию исключительно на посланном клиентом `senderId`/`isGM`.
6. Удостовериться в разграничении доступа при создании, обновлении, хранении, восстановлении и удалении.
7. Не использовать сторонний модуль socketlib как «гарантию безопасности» без проверки фактического сетевого поведения.
8. Сервисные записи по возможности не видны в чате; если выбранный серверно-безопасный транспорт не позволяет убрать их из чата без опасных хаков, **описать ограничение**, не жертвовать приватностью ради внешнего вида.

**Условие продолжения разработки:** адресный `User.query` является кандидатом для v1, но **не считается доказанно конфиденциальным до живой проверки сетевого поведения V14.364**; локальная персистентность GM — **согласованный компромисс по надёжности**, но не по утечкам. Codex должен реализовать модуль, собрать ZIP и обозначить его «требует ручной проверки конфиденциальности», если у него нет трёх реальных клиентов. Отсутствие возможности провести браузерный тест **не является основанием прекращать всю разработку**. Если проверка кода покажет, что адресные запросы в конкретной сборке передают приватный payload посторонним, режим приватности должен быть заблокирован (fail closed), а проблема — отражена в отчёте; запрещено заменять его обычным broadcast.

## Приложение A. Доставка, хранение и ограничения режима «Только мастеру»

### A.0. Решение после проверки Codex от 2026-10-09

Отказ от штатного закрытого серверного хранилища принят **только для приватной части версии 1**. Решение не отменяет режим «Только мастеру». Главное: приватное сообщение не должно попадать на клиент другого игрока даже в скрытом DOM/сокете/хранилище. Нельзя использовать `ChatMessage.whisper` как гарантированную изоляцию сетевого содержимого. Нельзя использовать модульный `game.socket.emit` с полем `recipient` для передачи секретов: документирован как broadcast.

### A.1. Доставка

- В V14 зарегистрировать `CONFIG.queries["right-to-speak.privateCreate"]`, `privateUpdate`, `privateCommand`, `privateSnapshot` и другие необходимые обработчики (точные имена по выбору разработчика), используя **публичный API `User.query`**. Регистрация имён строго с префиксом модуля.
- Автор создаёт секретную заявку **адресным** `game.users.activeGM.query(...)` к конкретному активному GM. Если несколько GM, передать копии отдельно каждому разрешённому активному GM через адресные запросы; сериализацию изменений вести у назначенного координатора GM. Точную архитектуру multi-GM описать, не подразумевать атомарной транзакции ядра.
- Обновления статуса приватной заявки возвращать её автору и GM также адресными `User.query`; не рассылайте ни одного публичного уведомления, содержащего событие или число секретных заявок.
- Не использовать core `ChatMessage` для приватной заявки; не сохранять приватные данные в shared `game.settings` (world), публичных документах, общем журнале или модульном broadcast.
- В handler проверять фактического отправителя на основании параметров официального API installed V14 (release 14.352 отмечает передачу sender ID/instance в User-query). Нельзя авторизовывать клиента только по произвольным полям `userId`, `isGM` или `ownerUserId` payload. Если идентичность sender из API выяснить нельзя, не включать привилегированные GM-команды или приватные операции до решения. Проверять целевой userId, роль, ownership, тип операции, размер полей и ревизию.
- При отсутствии активного GM тайную заявку не отправлять в общие каналы. Показать ошибку «Мастер не в сети» или «Не доставлено»; после восстановления игрок может повторить с тем же idempotency key. `ack` от GM выдаётся только после принятия заявки координатором.

### A.2. Хранение и восстановление

- GM хранит приватную очередь локально в **IndexedDB своего браузера**, пространстве имён worldId + GM userId. Это не серверное хранилище Foundry, оно НЕ синхронизирует очередь между компьютерами. От автора хранится исключительно его собственная приватная заявка и её статус в локальном хранилище автора.
- По reload **того же браузера** GM восстанавливает очередь из IndexedDB; локальные записи проверяются на срок, корректность и принадлежность миру. Когда автор онлайн, он может синхронизировать свой запрос с GM по адресному каналу без новых публичных событий. Удалять завершённые заявки по настройке/TTL; очищение очереди удаляет локальные записи.
- После удаления данных браузера, смены компьютера GM или при офлайне обоих участников восстановление приватной заявки **не гарантируется**. Отдельно предупреждать об этом в README/GM settings. В таких ситуациях автор должен иметь возможность отправить новую заявку. Для абсолютной долговечности потребуется отдельно проектируемое защищённое серверное хранилище; оно НЕ входит в v1.
- Клиентское хранение на устройстве мастера не защищает от другого человека с доступом к тому же профилю браузера, вредоносных расширений, взлома самого GM или администратора сервера. Это ограничения доверия, а не скрытая ошибка реализации. По возможности предусмотреть кнопку очистки локальных приватных данных.

### A.3. Публичные и приватные проекции

- Публичная очередь может храниться обычным механизмом мира, выбранным разработчиком с учётом прав и валидации. В ней НИКОГДА не должны появляться приватные записи, их ID, количество, тип, время, связь с другой заявкой или статус. Ни aggregate count, ни ревизии публичной очереди не изменяются вследствие тайного запроса.
- UI игрока видит свою приватную заявку (из локального состояния), GM видит все доставленные ему приватные записи, любой другой игрок — ноль сведений об их существовании.
- Переход **public→private** не может отменить уже случившееся раскрытие; явно предупредить. Переход **private→public** возможен только по явно подтверждённому действию и публикует лишь разрешённую проекцию.
- Отправку адресных данных не логировать в общую консоль; комментарии выводить как textContent и валидировать на длину.

### A.4. QA / правила выпуска

- Обязательно добавить unit-тесты: логические переходы статусов, ACL, ownership, idempotency и сериализация без приватного payload, устойчивость к повторному `CREATE`.
- **Живой тест** в 3 независимых сессиях (GM, Алиса, Боб): проверить websocket frames/Network (включая начальную загрузку world), DOM, client storage, global shared settings. Алиса отправляет GM-only запрос о Бобе; у Боба не должно быть данных/метаданных. Проверить ответы и статусы, reload GM, reconnect Alice, двойные отправки, offline GM. Одной проверки CSS недостаточно.
- Пока такой тест не пройден, Codex **всё равно пишет код, собирает ZIP** и честно указывает `BETA / приватность требует проверки в реальной Foundry V14.364`. Не заявлять, что безопасность проверена. Если в установленной версии `User.query` всё же раскрывает секрет посторонним, скрытый режим должен выключаться (fail-closed); нельзя незаметно заменить transport на broadcast.
- Тестовая сборка устанавливается администратором в test world; перед пробой на основной кампании — резервная копия User Data.
