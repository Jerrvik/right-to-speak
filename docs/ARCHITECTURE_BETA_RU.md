# Архитектура Right to Speak 0.1.0 BETA

## Проверенное в коде Foundry 14.364

В локальной установленной сборке `User.query` отправляет `userQuery` серверу, который берёт отправителя из аутентифицированного сокета и пересылает payload только сокетам указанного `User`. Обработчик клиента получает `context.user`, соответствующий серверному ID отправителя. Эти свойства проверены чтением кода `client/documents/user.mjs`, `client/documents/collections/users.mjs` и `dist/components/activity.mjs`. Официальные источники: [User.query](https://foundryvtt.com/api/v14/classes/foundry.documents.User.html), [CONFIG.queries](https://foundryvtt.com/api/v14/variables/CONFIG.queries.html), [release 14.352](https://foundryvtt.com/releases/14.352).

Это статическая проверка. Сетевой тест в трёх браузерных сессиях остаётся релизным блокером. Стандартный socket модуля не используется: [документация модулей](https://foundryvtt.com/article/module-development/) описывает его как broadcast.

## Разделение данных

| Данные | Где находятся | Кто получает |
|---|---|---|
| Полная активная очередь с комментариями | IndexedDB текущего профиля GM | GM этого профиля; другим активным GM отправляется адресная копия |
| Собственная заявка игрока | IndexedDB профиля автора | Автор |
| Публичная проекция активной очереди | `world` setting `right-to-speak.publicQueue` | Все клиенты мира |
| Координаты, свёрнутость, локальные опции | `localStorage`, ключ мир + пользователь | Текущий профиль браузера |

Публичная проекция содержит только ID, ID владельца, срочность, тип, цель, разрешённый статус, время создания и **публичный порядок без пропусков**. В ней нет комментария, признака приватной заявки, внутренней ревизии и времени правки. Создание, правка, подтверждение и закрытие тайной заявки не изменяют общий setting. Правка только комментария публичной заявки также не меняет публичный setting.

## Протокол

1. Клиент игрока адресно отправляет `CREATE_REQUEST` координатору GM. В создании уже задана видимость. GM проверяет `context.user`, схему и наличие активной заявки этого владельца.
2. GM присваивает время из синхронизированных часов `game.time.serverTime`, порядок и ревизию. Перед подтверждением любой заявки он успешно записывает полное состояние в IndexedDB; при отказе хранилища новые команды не принимаются.
3. Каждый переход сверяет `expectedRevision`; команды сериализуются очередью промисов координатора. Повторное создание с тем же ID возвращает уже принятую запись.
4. Статусы и полная заявка идут только автору и активным GM через `User.query`. Публичный setting обновляется лишь при изменении публичной проекции.
5. При reload GM читает IndexedDB того же профиля, затем добавляет публичную проекцию из setting. Другие GM запрашивают снимок у координатора. Автор синхронизирует свою заявку и при необходимости повторяет создание с прежним ID.

Заявка с `targetUserId` не доставляется целевому игроку только из-за привязки. Клиент выводит заметки через `textContent` и ограничивает длину на стороне координатора. Привилегии определяются по серверному `context.user`, а не по полям payload.

## Остаточные ограничения

- В IndexedDB нет серверной долговечности и синхронизации между компьютерами. Локальные снимки старше 30 дней игнорируются. Очистка профиля, смена устройства или потеря всех GM-копий может привести к потере приватной очереди. Авторский ресинк возможен только при доступном авторе и его локальной копии.
- Публичная очередь восстанавливается из world setting даже при потере GM-профиля, но личные комментарии и внутренние ревизии из одной публичной проекции не восстанавливаются полностью. Для полного восстановления нужен доступный автор с локальной копией; до синхронизации возможны конфликты ревизий.
- `game.time.serverTime` — оценка серверного времени после синхронизации, а не атомарная метка времени серверной базы.
- Координатор работает на клиенте GM. При сетевых разделениях, смене координатора и двух вкладках под одним GM-аккаунтом атомарная консистентность не гарантируется. Ревизии предотвращают обычные конфликты в рамках одного координатора.
- Человек с доступом к тому же профилю браузера, вредоносное расширение, администратор сервера или скомпрометированный GM выходят за пределы защищаемой модели. У разных участников должны быть независимые профили браузера.
- Если `QUERY_USER` отключён или IndexedDB автора/GM не работает, скрытая отправка завершается ошибкой. Если IndexedDB координатора GM недоступен, все новые команды отклоняются. Передача через broadcast не используется как запасной путь.
- Сетевые кадры, начальная загрузка мира, DOM и storage постороннего клиента в живой V14.364 ещё не проверены. До этого модуль помечен BETA.
